# Mock integration contract

This contract is for the first **demo-data-only** integration. It does not
define telemetry ingestion, production scheduling rules, or a production
optimizer transport.

## Canonical mock factory

Use the existing Supabase backend seed factory with slug
`demo-chocolate-factory` (`Demo Chocolate Factory`) as the integrated source of
truth. The factory's database UUID is generated by the backend database and is
the only canonical factory ID at runtime. The seeded UUIDs for machines,
processes, dependencies, orders, optimization records, schedules, and entries
are likewise canonical when those rows exist.

The generic SQLite `offline-demo-plant` seed remains a backend test/development
fixture, not a second integrated factory. The initial cross-component demo
must use the selected Chocolate factory and must not combine its records with
that generic fixture.

All rows and resulting schedules are synthetic demonstration data. Their
values are not real plant telemetry, energy prices, savings, or operational
instructions.

## Backend API contract

Base path: `/api/v1`. Factory-scoped resources use
`/factories/{factoryId}/...`, where `factoryId` is the canonical UUID.

Successful responses contain `{ "data": ..., "meta"?: ... }`. Errors contain
`{ "error": { "code": ..., "message": ..., "details"?: ... } }`. Clients must
not treat an HTTP failure, invalid response, or missing `data` envelope as an
empty dataset.

The API keeps the database's snake_case fields. Relevant records:

- Factory: `id`, `slug`, `name`, `timezone`, `currency`, `config`, `metadata`.
- Machine: `id`, `factory_id`, `slug`, `name`, `type`, `rated_power_kw`,
  power/runtime bounds, `availability`, and `metadata`.
- Process: `id`, `factory_id`, `slug`, `name`, `duration_minutes`,
  `machine_id`, `power_requirement_kw`, `production_quantity`, and `unit`.
- Dependency: `id`, `factory_id`, `process_id`, `depends_on_process_id`,
  `dependency_type`, and `lag_minutes`.
- Production order: `id`, `factory_id`, `reference`, `product`, `quantity`,
  `unit`, `due_at`, `priority`, and `status`.
- Schedule: `id`, `factory_id`, `version`, `status`, `horizon_start`,
  `horizon_end`, `optimization_request_id`, and `optimization_result_id`.
- Schedule entry: `id`, `schedule_id`, `machine_id`, `process_id`,
  `production_order_id`, absolute `starts_at`/`ends_at`, energy/cost/quantity,
  and `sequence`.

API machine, process, order, dependency, schedule, and entry IDs remain UUIDs
in every client. Names and slugs are display/mapping attributes, never
identity substitutes.

## Client mapping and status meanings

- The frontend API row mapper preserves all entity UUIDs and converts
  snake_case field names into presentation references. It must not invent
  utilization, current job, solar use, KPI values, or schedule data when the
  backend does not return them.
- Factory-3D's `machine_id` is the backend machine UUID. Its optional
  `layout_id` is a separate scene geometry key. A fixed slug-to-layout mapping
  selects geometry; it never changes the canonical machine identity.
- The backend machine schema currently has no operational-status or live
  power-draw field. Therefore API-mapped 3D machines use `unknown` /
  `Not reported`, have no current draw, and have no inferred production
  duration. `rated_power_kw` is rated capacity, not actual load.
- A schedule entry is a planned interval, not proof that a machine is
  operating. Show absolute offset-aware timestamps, and label any
  schedule-derived visual state as planned.
- Existing frontend and Factory-3D mock providers remain explicit
  development/testing fixtures. They are not an API-error fallback.

## Optimizer boundary contract

The integrated optimizer call will be made by the backend from rows belonging
to the selected factory. It must pass backend UUID strings as optimizer
`factory_id`, `machine_id`, and `process_id` values; string representation does
not change identity. The optimizer's standalone `factory_data.py` sample is
not the integrated data source.

The Python public input is `{ "factory": ..., "energy": ..., "options": ... }`
and its public output is the versioned API v2 envelope with baseline and
optimized results. The backend maps its `OptimizationProblem` into that input
and validates/projects the response back into `OptimizationSolution`.

For the approved mock-only integration, the Chocolate seed adjusts
`grind-nibs` 45→60 minutes, `mould-shell` 35→60, `cool-and-demould` 25→30,
and `pack-retail` 40→30 so every duration fits the optimizer grid. Each
15-minute synthetic solar reading is `round(hourly_kw * 5) / 20` kWh, making
four readings sum to an hourly solar value in 0.2 kW increments; the source
label is `simulated`. The off-peak tariff now runs 22:00–07:00, and shoulder
runs 07:00–22:00. Existing machine availability calendars are unchanged.
These are demo fixture accommodations, not rules for future real factory data.

The local backend adapter invokes `optimizer.public_api.optimize_request`
through a bounded Python child process using JSON on stdin/stdout. HTTP mode
remains available and retains its prior configuration behavior. The selected
mode is explicit via `BYTEME_OPTIMIZER_TRANSPORT`; local Python mode requires
`BYTEME_OPTIMIZER_ENABLED=true`, a configured Python executable, and the
optimizer working directory. The adapter rejects unsupported/incomplete
problems instead of rounding, inventing missing intervals, or silently
substituting defaults.

Python scheduling uses its existing half-hour grid. The backend adapter
currently accepts exactly a 24-hour, UTC-hour-aligned horizon; complete
site-level 15-minute solar coverage; solar values representable at 0.2 kW
precision; 30-minute process durations; supported `cost`/`solar` objectives;
and only zero-lag finish-to-start dependencies. The backend passes the
objective explicitly to the Python public API.

The result mapper accepts only API v2 `OPTIMAL`/`FEASIBLE` results with one
valid entry for every submitted process. It preserves backend process and
machine UUIDs, verifies machine assignments, durations, power, quantity,
dependency ordering, and unit-capacity non-overlap, and maps optimizer
relative hours to offset-aware UTC timestamps from the submitted horizon.
Production-order IDs remain null because no process/order relationship exists
in the current schema. Persisting this solution as schedule database records
is a later phase, not part of this adapter boundary.

Known optimizer limitations remain explicit: machine availability calendars
are informational and are not enforced; machine power/compatibility fields
are informational; Python defaults processes to flexible and machine
capacity to one because the backend has no corresponding fields; production
orders are not related to processes; and demand charges, fixed charges, and
taxes are not included in the energy-cost objective. Backend energy
consumption readings are retained but are not used as process energy. Do not
treat these demo outputs as operational schedules, energy savings, or real
plant telemetry.

The Phase 6 UAT's baseline/optimized impact panel is a model-based comparison
of the persisted schedule entries. It reports process energy, optimizer-reported
solar/grid allocation and tariff-weighted energy cost, simultaneous scheduled
process power, completion timing, and schedule shifts. The panel verifies that
persisted entries retain the raw optimizer's per-process values; it does not
recompute tariff costs. Its solar denominator is the synthetic solar profile
supplied to the optimization. Unallocated profile energy is not evidence of
physical curtailment, and scheduled process power is not measured factory
demand. The displayed energy cost excludes demand charges, fixed charges, and
taxes. These modeled comparisons must not be described as measured savings,
utility-bill savings, or verified plant impact.

There is currently no process-to-production-order relationship in the
database. An optimizer/schedule entry must therefore keep
`production_order_id: null` unless a real explicit association is supplied;
never infer it from product names, quantities, or order priority.

## Phase 5 Factory-3D launch contract

Factory-3D remains a separate React 19 application. The Phase 6 frontend and
Factory-3D authenticate independently through Supabase Auth using only the
browser-safe publishable key. Each application sends the signed-in user's
access token only in Backend `Authorization` headers. The Phase 6 launcher
passes canonical `factoryId` and `scheduleId` UUIDs only; credentials and
tokens never enter the URL. Browser configuration stays in ignored local env
files and must never contain a secret/service-role key. The live Phase 6 path
does not use offline mode.

The 3D app requests the scoped machine list and exact selected schedule detail,
including its entries. It retains backend UUIDs as entity IDs and uses the
backend machine slug only to choose an existing scene layout key. A machine
with no crosswalk entry stays in backend state but is listed as unplaced; no
scene machine or position is substituted. Machine state and current power
remain unknown without telemetry. Schedule entries are shown as planned
intervals with their offset-aware timestamps; they never imply live operation.
API mode disables status simulation, debug edits and demo product animation.
API failures are visible and never fall back to mock machine/schedule data.

The `/phase6` frontend path is a narrow authenticated UAT surface. It captures
one read-only canonical snapshot, gates a single optimization POST behind the
Auth and data checks, and verifies persisted records through the Backend API.
The frontend and 3D applications remain separate, avoiding the React 18 /
React 19 embedding boundary.

## Phase boundaries

The backend optimizer adapter is the local Phase 2 boundary. Phase 3 persists
raw optimizer results and draft schedules. Phase 4 owns the frontend's broader
backend data/API integration; the Phase 5 launcher does not silently replace
the existing dashboard data or mock view models. Phase 5 connects the separate
3D app to a selected backend factory and schedule without changing optimizer
semantics, database schemas, or the authentication model.
